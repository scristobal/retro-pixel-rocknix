013 - AGENT WORKFLOW
==============================================================

This file is for coding agents picking up the RetroPixel Pocket port.
Follow it before making changes.

Branch rule
-----------
All RetroPixel Pocket commits belong on:

    retropixel-pocket-support

Do not commit RPPocket work on 'next'.  The 'next' branch is reserved
as a clean mirror of ROCKNIX upstream's next branch:

    next == origin/next == upstream/next

If the checkout is not on retropixel-pocket-support, switch to it
before editing or committing.  If new upstream work is needed, update
next from upstream/next first, then rebase or merge
retropixel-pocket-support over it.

Debug notes, decision logs, commit log
--------------------------------------
Commit messages carry the final per-change debug summary for committed
work.  Each hardware-facing commit should explain:

    - the observed problem or new evidence
    - the hypothesis being tested
    - what changed
    - what the user should test next, if applicable

The debug/*.txt files are not all the same kind of document:

    - current_state.txt records the latest known status: branch state,
      latest known good image, what works, what is broken, open
      questions, and the next concrete test.  Update it only when a
      result becomes accepted current project state, usually when a
      tested change is ready to commit or has just been committed.
    - Topic notes record stable knowledge and conclusions: 005 for
      boot flow, 006 for DTS, 007 for panel, 008 for power, 009 for
      audio, 010/011 for input, 012 for debug tooling.
    - Decision logs record active trial-and-error for an unresolved
      investigation.  For Wi-Fi, use 014-wifi-decision-log.txt.

Do not append blow-by-blow experiment logs to current_state.txt.  Put
active unresolved experiments in the relevant decision log, then
collapse the final accepted outcome into current_state.txt and the
commit message once the result is tested.

Do not leave important reasoning only in chat.  The next agent should
be able to recover the state from current_state.txt, the relevant
topic notes, and git history.

Stock image instrumentation
---------------------------
When ROCKNIX behavior is stuck behind hardware uncertainty, use the
working stock image as an oracle before continuing a broad guess
matrix.  Do this on a copy only, never on the pristine stock reference
under original-sources/.

The proven stock workflow is documented in:

    debug/017-stock-image-instrumentation.txt

Key details:

    - pre-expand the stock STORAGE partition before adding files
      under /storage, otherwise first-boot resize/init may fail
    - inject /storage/.config/custom_start.sh as a passive logger
    - boot stock and confirm the feature still works
    - after the user reinserts the SD, inspect:
          /run/media/$USER/STORAGE/rppocket-stock-debug-*.txt

Use stock captures to identify runtime GPIO, regulator, module, USB,
and timing behavior.  Start a new numbered decision log for any new
stock-derived ROCKNIX experiment.

Build and device-test rule
--------------------------
After a code change, decide whether the device must be reflashed:

    Ask the user to run:

        sudo ./debug/pre.sh --flash /dev/sdX

    only when the changed result must be written into a fresh image or
    storage reset is important.  Examples: DTS, kernel patch, kernel
    config, u-boot, bootloader files, bundled quirks, rootfs defaults,
    or anything that needs a clean first-boot state.

    Ask the user to run:

        sudo ./debug/pre.sh /dev/sdX

    when the existing SD image is still valid and only the debug hook
    or local ROM copy needs refreshing.

After the user boots and powers down the device, expect them to insert
the SD into the host and tell you it is inserted.  Mount the SD and
inspect the full captures directly:

    udisksctl mount -b /dev/sdX1
    udisksctl mount -b /dev/sdX2

Read the boot-partition captures and storage logs before making the
next hardware-facing change.  Common paths are:

    /run/media/$USER/ROCKNIX/dmesg-boot.txt
    /run/media/$USER/ROCKNIX/dmesg-late.txt
    /run/media/$USER/ROCKNIX/journalctl-boot.txt
    /run/media/$USER/ROCKNIX/rppocket-debug.txt
    /run/media/$USER/ROCKNIX/rppocket-late.txt
    /run/media/$USER/ROCKNIX/rk3326-funnyplaying-rppocket.dtb
    /run/media/$USER/STORAGE/.cache/log/

Agent response pattern
----------------------
For each hardware-facing iteration:

    1. Make the smallest code/docs change that tests one hypothesis.
    2. Append the experiment to the relevant decision log when the
       work is still exploratory.  Update current_state.txt only if
       the current project state or stable conclusions changed.
    3. Build if needed.
    4. Tell the user exactly which pre.sh command to run.
    5. Wait for the user to insert the SD after device testing.
    6. Mount the SD, read full logs/DTB, and append the result to the
       decision log.  Update current_state.txt / topic notes only with
       accepted current state and durable conclusions.
    7. Only then decide the next change.
    8. When committing, put the detailed debug log for the change in
       the commit message.

Do not ask for --flash by reflex.  It is correct when the image/rootfs
must change, but it costs the user a full flash and first-boot cycle.
