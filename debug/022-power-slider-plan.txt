022 - POWER SLIDER INVESTIGATION PLAN
==============================================================

Goal
----
Make the RPPocket power slider behave consistently across the complete
power lifecycle:

    - short slide/release while running: enter a low-power state quickly
    - short slider action while suspended: wake and resume quickly
    - approximately 5 second hold while running: orderly poweroff
    - slider action while powered off: cold boot
    - PMIC emergency cutoff/reset remains available for a wedged system

The immediate priority is reliable short-action suspend/resume. Do not
combine input semantics, Linux suspend/wake, userspace policy, orderly
shutdown, and PMIC hard cutoff in one hardware experiment.


Known baseline
--------------
Accepted ROCKNIX image:

    - target/ROCKNIX-RK3326.aarch64-20260802-a.img.gz
    - sha256 29aa4aa3c9d4dc99016c539ce1183e4b44fd9c06a887bb7d84310448a154b361
    - User confirmed this refreshed image works before power changes.

Reported behavior on that baseline (2026-08-03):

    - the first short slider action after boot immediately blacks the screen
    - later short slider actions do not visibly recover the device
    - a very long hold eventually resets the device

This proves that the running system sees enough of the first action to
start its sleep policy. It does not yet prove whether the machine reaches
deep suspend, fails before completing suspend, wakes with a dead display,
or never receives a wake event. The very long action currently looks like
the PMIC emergency path, not an orderly Linux reboot.

ROCKNIX hardware/kernel facts:

    - The slider is exposed as "rk805 pwrkey" even though the board PMIC
      is RK817; the shared driver reports KEY_POWER press/release IRQs.
    - CONFIG_INPUT_RK805_PWRKEY=y, CONFIG_SUSPEND=y, CONFIG_PM_DEBUG=y,
      CONFIG_PM_SLEEP_DEBUG=y, and CONFIG_RTC_DRV_RK808=y.
    - The RPPocket RK817 node has wakeup-source and the default, sleep,
      power-off, and reset pinctrl states.
    - Suspend regulator states are present in the compiled DTB.
    - The built Linux 6.12.79 rk805-pwrkey driver calls
      device_init_wakeup(), but does not assign its falling IRQ with
      dev_pm_set_wake_irq(). The RK3576 tree carries a small candidate
      patch that does so; it is a reference, not proof for RPPocket.
    - The RK3326 kernel already builds
      031-px30s-suspend-wakeup-config.patch and
      CONFIG_ROCKCHIP_PM_CONFIG=y, but the current RPPocket DTS has no
      rockchip-suspend node, so that driver has no RPPocket device to
      probe and no RPPocket values to forward to BL31.

ROCKNIX userspace facts:

    - The built image sets systemd-logind HandlePowerKey=suspend.
    - Common RK3326 autostart defaults system.suspendmode to mem and writes
      SuspendState=mem standby freeze.
    - input_sense also notices KEY_POWER and invokes rocknix-fake-suspend,
      but fake suspend exits immediately whenever hardware suspend mode is
      not "off". Therefore the current mem-mode blackout is not expected
      to be the fake-suspend input-grab self-lockout.
    - EmulationStation exposes Device Suspend Mode, so freeze/standby/mem
      can be tested without rebuilding.
    - systemd 255 already supports HandlePowerKeyLongPress=poweroff with a
      five-second timer. When that differs from HandlePowerKey=suspend,
      logind waits for release before treating an action as short. A custom
      long-press daemon should not be the first implementation.

Working-stock evidence:

    - The actual v1.1.3 stock image's
      rk3326-rppocket_v6_0-linux.dtb (SHA-256
      cd12a289f64051f2b9f4b6654404fad4513252eea500553b8d5bc771f7d9d5f4)
      contains an enabled rockchip-suspend node with:

          compatible = "rockchip,pm-px30"
          rockchip,sleep-debug-en = <1>
          rockchip,sleep-mode-config = <0x20702>  (132866)
          rockchip,wakeup-config = <0x85>         (133)

      The mode enables ARM-off, PMU hardware PLL power-down, PMU-alive
      32 kHz, oscillator disable, and PMIC low-power handling. The wake
      mask enables cluster, GPIO, and USB wake.
    - The stock rockchip_pm_config driver forwards those values to BL31
      during probe. Its RPPocket rk8xx-pwrkey driver does not itself call
      device_init_wakeup(), enable_irq_wake(), or dev_pm_set_wake_irq().
    - This makes the missing stock-derived BL31 configuration a strong
      candidate, but stock suspend/wake behavior must still be confirmed
      on the device before calling it the root cause.


2026-08-03 - Baseline failure log inspection
--------------------------------------------
Hypothesis:
    The first slider action reaches real mem suspend, while later actions
    fail to wake it; the visible blackout is not ROCKNIX fake suspend.

Inspection:
    Mounted the returned 20260802 baseline card read-only. Its effective
    configuration was:

        system.suspendmode=mem
        SuspendState=mem standby freeze

    The card's compiled RPPocket DTB contains RK817 wakeup-source and all
    PMIC pinctrl states, but no rockchip-suspend node.

Observed result:
    The persistent messages log contains four independent failure cycles.
    At 14:51:49, 14:54:52, 15:18:57, and 17:35:52 it records:

        input_sense: *(KEY_POWER), value 1: Pressed
        rocknix-fake-suspend: Hardware suspend enabled, exiting
        sleep: Preferring the active WIFI network on reconnect.
        sleep: Disabling WIFI.
        sleep: Input sense: stop
        sleep: Power state: stop
        sleep: Modules: stop

    None of those cycles contains any ROCKNIX post-sleep action. Each is
    followed by a fresh boot, respectively about 69 seconds, 64 seconds,
    5 minutes 53 seconds, and 49 seconds later. This matches the user's
    forced-reset recovery and rules out fake-suspend input grabbing as the
    immediate failure. The readable syslog does not contain the final
    kernel PM line, so it cannot distinguish a hang during late suspend
    from successful deep entry with no wake IRQ.

    /storage/.cache/log/sleep.log contains a harmless missing-glob error
    for the absent FunnyPlaying sleep.d/pre quirk. The hook does not use
    set -e and runs a successful touch after that call, so this is not an
    explanation for the failed wake. No files on the card were changed.

Decision / next step:
    The userspace trigger path is proven. Test freeze on the unchanged
    image next. A successful freeze wake will isolate the remaining issue
    to mem/platform firmware and prioritize the stock rockchip-suspend
    node; a failed freeze wake will prioritize pwrkey wake-IRQ wiring.

    ROCKNIX pre-sleep sequence through "Modules: stop", but again has no

Decision / next step:
    Failure in freeze makes the missing BL31 mem configuration an
    insufficient explanation for this test and prioritizes Candidate B.

    trial.

2026-08-03 - First pm_test=devices attempt was invalid
-------------------------------------------------------
Hypothesis:
    A devices-level PM test should reverse itself after five seconds. If it
    still leaves the panel black, the failure is in device suspend/resume
    rather than hardware wake signaling.

Requested test / visible result:
    Installed a one-shot hook that selected pm_test=devices and requested
    freeze through systemctl. The screen did not recover. A short action and
    then a longer action had no visible effect. A later long action produced
    a fresh boot at 01:21:25, after which the user shut down from the menu.

Observed log result:
    This test did not actually retain pm_test=devices until kernel suspend.
    The hook selected devices at 01:18:28, but `systemctl suspend` returned
    to the hook during that same second. The hook then captured its "after"
    state and reset pm_test to none. ROCKNIX's pre-sleep hook did not begin
    until 01:18:29. The device therefore entered the already-failing normal
    freeze path, not the self-returning devices test.

    The pre-attempt capture still confirms that the RK817 parent, rk805-
    pwrkey child, and RK808 RTC child all expose power/wakeup=enabled. The
    nested IRQs are present as IRQ 31 (fall), IRQ 32 (rise), and IRQ 36
    (RTC), under GPIO parent IRQ 30.

Decision / next step:
    Do not treat the visible failure as a devices-stage result. Correct the
    hook to keep pm_test=devices selected while writing `freeze` directly to
    /sys/power/state. That write blocks until the kernel reverses the device
    phase, avoiding systemctl's asynchronous ordering and all hardware wake
    dependencies.

Interpretation / next step:
    Upstream's DPM watchdog wraps normal device suspend/resume callbacks, but
    not `dpm_prepare()`. The suspend path calls `suspend_console()` and then
    `dpm_prepare()` before reaching the watched callbacks. `dpm_prepare()` can
    block acquiring a device lock or inside a driver's prepare callback. This
    explains a permanent hang with no watchdog panic and narrows the failure
    to before the first normal suspend callback.

    Extend the temporary DPM watchdog around each `device_prepare()` call so
    it records the exact current device even if acquiring that device's lock
    blocks. The Mali/genpd path remains the leading suspect: its runtime-PM
    workers repeatedly warn in `disable_gpu_power_control()` and then double-
    disable `clk_gpu` shortly before suspend, which can leave the GPU device
    lock held when system PM enters prepare. Do not change GPU behavior yet;
    first obtain the prepare-stage device name and blocked-task stack.

Phase 1 - Preserve and classify the current failure
---------------------------------------------------
First inspect the already-reported failure before changing an image. When
the current SD card is available, read its persistent journal directly and
look for:

    - "Power key pressed short" from logind
    - systemd-suspend start and the ROCKNIX pre-sleep hook
    - "PM: suspend entry" and the selected mem_sleep state
    - any suspend abort/error
    - "PM: suspend exit" and the ROCKNIX post-sleep hook
    - a clean reboot request versus an abrupt next boot after the long hold

Capture the following before another suspend attempt:

    - non-grabbing KEY_POWER press/release timestamps
    - /proc/bus/input/devices and udev power-switch tags
    - /proc/interrupts for the RK817 parent and pwrkey nested IRQs
    - /sys/kernel/debug/wakeup_sources
    - the RK817 and rk805-pwrkey power/wakeup sysfs files
    - /sys/power/state and /sys/power/mem_sleep
    - effective systemd sleep and logind configuration
    - active inhibitor locks

Use persistent pre/post markers with sync so a forced reset still tells us
whether post-resume userspace ever ran. Do not use evtest --grab; it can
steal the only wake/policy input and create a false failure.

Decision gate:

    - suspend entry with no exit means wake or firmware is the first issue
    - suspend exit plus SSH/ping/audio but a black panel means display
      resume is the first issue
    - an error before suspend entry means fix that driver/hook first
    - no logind action means fix input/udev/userspace policy first


Phase 2 - Try the safe suspend-state matrix without rebuilding
--------------------------------------------------------------
Use EmulationStation's Device Suspend Mode setting and test one state per
boot. Start with freeze, then standby only if the kernel exposes it. Leave
the currently failing mem test until last.

For each state:

    1. short slide/release while running
    2. wait five seconds after the display goes dark
    3. short slide/release to wake
    4. check display, controls, audio, Wi-Fi, clock, and running game state
    5. if the panel stays black, check ping/SSH or audio before forcing reset

If freeze wakes reliably, it is a useful immediate fallback: add a
FunnyPlaying device suspend-mode quirk that defaults new installs to
freeze while preserving the user's ability to override it. Freeze is
suspend-to-idle and will save less power than working mem/deep suspend, so
it is a safe interim behavior, not the final deep-standby result.

If supported, use an RK817 RTC wake alarm for one controlled mem attempt.
An RTC resume with no slider resume isolates the pwrkey wake path; failure
to resume from either source points instead at platform/BL31 suspend.


Phase 3 - Fix mem/deep wake one variable at a time
--------------------------------------------------
Choose the first candidate from the Phase 1/2 evidence; do not apply both
at once.

Candidate A - restore the stock RPPocket BL31 configuration:

    Add a board-local rockchip-suspend node to
    rk3326-funnyplaying-rppocket.dts using the exact vendor DTB values:

        compatible = "rockchip,pm-px30"
        sleep-mode-config = <132866>
        wakeup-config = <133>

    Use sleep-debug-en=<1> for the stock-matching diagnostic trial if its
    output is useful, then disable debug in the production result unless it
    is required. The already-built ROCKCHIP_PM_CONFIG driver will forward
    the values to BL31. This is preferred first if freeze/key wake works but
    mem does not, because the working-stock DTB contains this node and the
    current RPPocket DTB does not.

Candidate B - bind the pwrkey falling IRQ as a wake IRQ:

    Backport the minimal rk805-pwrkey dev_pm_set_wake_irq() change into the
    RK3326 patch series, including linux/pm_wakeirq.h and error handling.
    This is preferred first if even freeze shows that the pwrkey interrupt
    is not treated as a wake event. Confirm that the nested regmap IRQ
    propagates wake enable to the GPIO0 PB2 parent IRQ.

For either candidate:

    - build with make docker-RK3326
    - inspect the applied kernel source
    - decompile the built RPPocket DTB and verify only the intended nodes
    - flash manually with debug/pre.sh; never use SDWire
    - test only suspend entry and one slider wake before broader testing
    - reinsert the SD and inspect persistent logs before the next change

Fallback only if both isolated candidates fail:

    - boot the copied stock debug image and first confirm stock short
      suspend/wake really works
    - compare stock and ROCKNIX RK817 interrupt masks and status registers
    - compare nested pwrkey IRQ wake enable and GPIO0 PB2 parent IRQ state
    - inspect BL31/ATF versions and wake reasons
    - compare PMIC sleep pin state and regulator state at suspend entry

Do not copy additional values from another handheld. The exact RPPocket
vendor DTB and stock runtime are the oracle.


Phase 4 - Validate resume quality and latency
---------------------------------------------
After a candidate wakes once, require at least ten consecutive cycles.
For every cycle verify:

    - no unintended reboot and no immediate re-suspend loop
    - display and backlight recover at the expected brightness
    - controls, audio, Wi-Fi, clock, and storage recover
    - an emulator/game resumes without lost state
    - wake reason and IRQ counts identify the slider

Measure visible press-to-dark and press-to-image latency. Then do a longer
suspend and compare battery drain for freeze versus mem so the chosen
default is based on both reliability and power savings.


Phase 5 - Finalize short/long userspace semantics
-------------------------------------------------
Only after wake is reliable, add a FunnyPlaying-specific logind quirk:

    HandlePowerKey=suspend
    HandlePowerKeyLongPress=poweroff

The existing systemd five-second timer should distinguish the actions:

    - release before five seconds: suspend on release
    - hold through five seconds: orderly systemd poweroff

Verify exactly one action per physical slide, no duplicate handling by
input_sense/EmulationStation, no release-edge resume loop, and no race
between suspend and poweroff. Preserve the PMIC emergency cutoff/reset for
cases where Linux is wedged.


Phase 6 - Poweroff and cold-boot validation
-------------------------------------------
After orderly shutdown verify:

    - PMIC power-off pinctrl is selected
    - rails and display actually turn off rather than entering suspend
    - no filesystem errors appear on the next boot
    - slider cold-boots reliably with and without USB power attached
    - repeated poweroff/powerup cycles do not become a reboot loop

Cold boot is primarily PMIC and bootloader behavior. Do not add Linux
userspace workarounds unless evidence shows Linux leaves the PMIC in the
wrong power-off state.

---------------------------------------
The short-action feature is accepted only after ten reliable cycles and
one longer soak with display, controls, audio, Wi-Fi, timekeeping, running
game, and storage all intact. The final policy must retain orderly
five-second shutdown and emergency PMIC cutoff.
