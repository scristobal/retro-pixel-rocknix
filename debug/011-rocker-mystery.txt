011 - ROCKER MYSTERY (VOLUME SOLVED, BRIGHTNESS UNRESOLVED)
==============================================================

Problem statement
-----------------
The RetroPixel Pocket has two physical "rockers" (small flat tabs you
can tilt up, tilt down, or push straight in):
    - Volume rocker
    - Brightness rocker

Each is mechanically a 3-action switch (up tilt, down tilt, centre
press), so 6 actions total across both rockers.

We can't get all 6 actions to fire predictable, consistent keycodes.

What we know about the candidate GPIOs
--------------------------------------
The factory BSP joypad node lists six GPIOs that are "rocker-like" —
i.e. not the D-pad, ABXY, L, R, SELECT, or START:

    gpio2 PA0     BSP label "BACKUP"        BSP linux,code BTN_TRIGGER_HAPPY5
    gpio2 PA1     BSP label "BACKDOWN"      BSP linux,code BTN_TRIGGER_HAPPY6
    gpio2 PA2     BSP label "F3"            BSP linux,code BTN_TRIGGER_HAPPY3
    gpio2 PA4     BSP label "F4"            BSP linux,code BTN_TRIGGER_HAPPY4
    gpio3 PB2     BSP label "TOP-LEFT2"     BSP linux,code BTN_TL2
    gpio3 PB7     BSP label "TOP-RIGHT2"    BSP linux,code BTN_TR2

The BSP labels are misleading — they were inherited from the RG351MP /
ODROID-GO Super reference design which had L2/R2 and brightness keys
in a different layout.  On RPPocket those names DO NOT correspond to
the physical actions.

Test 1 — captures during boot (commits 4d983b6f34 + 3d6450b517)
----------------------------------------------------------------
We ran 'evtest --grab' for 60s (later 120s) on every /dev/input/event*
during boot, asked the user to press each rocker action in a
documented order, and read the captured logs back from the SD.

Two consecutive captures both produced this pattern (filtered to
press-down events only):

    User intent                    Fired GPIO    Fired keycode
    ---------------------------    ----------    -------------
    "Volume tilt UP"               gpio3 PB7     BTN_TRIGGER_HAPPY4
    "Volume tilt DOWN"             gpio2 PA0     KEY_BRIGHTNESSUP
    "Volume centre press"          gpio2 PA1     KEY_BRIGHTNESSDOWN
    "Brightness tilt UP"           gpio3 PB2     BTN_TRIGGER_HAPPY3
    "Brightness tilt DOWN"         (no event fired)
    "Brightness centre press"      (no event fired)

So 4 out of 6 actions fire some GPIO; the remaining 2 brightness-side
actions don't fire any of the 18 button GPIOs we have wired up.
PA2 / PA4 in particular never fire across two test runs.

Based on those captures we shipped a "best guess" mapping (commit 3d6450b517):

    gpio3 PB7  -> KEY_VOLUMEUP                (vol tilt UP)
    gpio2 PA0  -> KEY_VOLUMEDOWN              (vol tilt DOWN)
    gpio2 PA1  -> BTN_TRIGGER_HAPPY1          (vol centre)
    gpio3 PB2  -> KEY_BRIGHTNESSUP            (brt tilt UP)
    gpio2 PA2  -> KEY_BRIGHTNESSDOWN          (brt tilt DOWN, GUESS)
    gpio2 PA4  -> BTN_TRIGGER_HAPPY2          (brt centre, GUESS)

Test 2 — real-use feedback after that mapping shipped
-----------------------------------------------------
With the above DTS, the user reported on actual usage:

    "Volume centre press"          increases system volume
                                   (i.e. some GPIO is firing KEY_VOLUMEUP,
                                   so PB7 fires when they press the
                                   volume rocker centre)

    "Brightness up tilt"           decreases system volume
                                   (i.e. some GPIO is firing KEY_VOLUMEDOWN,
                                   so PA0 fires when they press the
                                   brightness rocker UP)

This contradicts test 1.  Either:

    (A) The physical actions the user labelled in test 1 don't
        correspond to what they label the same way today.  The
        rockers are small and ambiguous to feel: pushing "up" on a
        rocker often partially engages a centre switch; pushing
        "centre" partially engages an edge switch.
    (B) The rockers have only 1 or 2 distinct switches each, not 3.
        What we believed were three separate physical actions might
        be just one (or two) reachable by different finger positions.
    (C) The rockers are on different GPIOs than the BSP suggests
        (i.e. PA2/PA4 are not wired at all on RPPocket; the brightness
        rocker uses GPIOs we haven't enumerated).

We DO NOT know which of A, B, C is correct.

Test 3 — delayed non-grabbing evtest capture
--------------------------------------------
debug/pre.sh was updated to run plain evtest on all /dev/input/event*
nodes for a 240 second window after boot, without EVIOCGRAB.  The
user confirmed they pressed all six groups in order, 5 presses each:

    1. volume upper edge       -> KEY_VOLUMEDOWN      (gpio2 PA0)
    2. volume lower edge       -> BTN_TRIGGER_HAPPY1  (gpio2 PA1)
    3. volume straight press   -> KEY_BRIGHTNESSUP    (gpio3 PB2)
    4. brightness upper edge   -> no event
    5. brightness lower edge   -> no event
    6. brightness straight     -> no event

No KEY_VOLUMEUP (gpio3 PB7), KEY_BRIGHTNESSDOWN (gpio2 PA2), or
BTN_TRIGGER_HAPPY2 (gpio2 PA4) events appeared.  The power key fired
later in the same capture, proving the capture was still alive.

Working conclusion: the volume rocker is wired to gpio2 PA0, gpio2
PA1, and gpio3 PB2.  The brightness rocker is either not wired to the
six BSP rocker GPIOs we know about, is mechanically not actuating, or
uses a path we are not currently monitoring.

Test 4 — flash feedback on the Test 3 mapping
---------------------------------------------
The Test 3 mapping put:

    gpio2 PA0  -> KEY_VOLUMEUP
    gpio2 PA1  -> KEY_VOLUMEDOWN
    gpio3 PB2  -> BTN_TRIGGER_HAPPY1

After a rebuild and flash, the user reported:

    "somehow volume up/down is in the brightness rocker instead of
    the volume rocker"

That disproves the Test 3 physical-label interpretation.  The raw
events were real, but the PA0/PA1/PB2 group belongs to the physical
brightness rocker, not the physical volume rocker.

Temporary DTS test mapping:

    gpio2 PA0  -> KEY_BRIGHTNESSUP
    gpio2 PA1  -> KEY_BRIGHTNESSDOWN
    gpio3 PB2  -> BTN_TRIGGER_HAPPY2
    gpio3 PB7  -> KEY_VOLUMEUP
    gpio2 PA2  -> KEY_VOLUMEDOWN
    gpio2 PA4  -> BTN_TRIGGER_HAPPY1

That mapping was rebuilt and flashed next; Test 5 covers the result.

Test 5 — vendor DTS check after volume still did nothing
--------------------------------------------------------
The swapped Test 4 mapping made the physical volume rocker do
nothing.  Re-checking the original RPPocket kernel source found the
missing piece in:

    original-sources/extpackage/linux-kernel-rppocket/arch/arm64/boot/dts/rockchip/rk3326-rppocket_v6_0-linux.dts

That DTS has the odroidgo3-joypad node we had been copying, but it
also has a separate commented rg351-keys node for volume:

    gpio3 PD3 -> KEY_VOLUMEUP
    gpio3 PC4 -> KEY_VOLUMEDOWN

The same file later shows those two pins as commented alternatives
under the BACKUP/BACKDOWN entries before PA0/PA1 were selected for
the joypad node.  This explains the failed tests: PA0/PA1/PB2 are
real physical contacts, but they are not the volume rocker; the
physical volume up/down contacts were never present in our gpio-keys
node or pinctrl list.

Test 6 — vendor volume pins confirmed
-------------------------------------
After rebuilding with the vendor DTS volume pins, the user confirmed:

    Volume upper/lower rocker actions work.
    Volume centre press does nothing.
    Brightness rocker does nothing visibly.

The boot logs from that image confirm gpio-keys registered:

    gpio3 PD3 -> VOL-UP
    gpio3 PC4 -> VOL-DOWN
    gpio3 PB7 -> VOL-CLICK
    gpio2 PA0 -> BRIGHTNESS-UP
    gpio2 PA1 -> BRIGHTNESS-DOWN
    gpio3 PB2 -> BRIGHTNESS-CLICK

Final DTS mapping for now:

    gpio3 PD3 -> KEY_VOLUMEUP
    gpio3 PC4 -> KEY_VOLUMEDOWN
    gpio3 PB7 -> BTN_TRIGGER_HAPPY1  (unconfirmed volume click)
    gpio2 PA0 -> KEY_BRIGHTNESSUP
    gpio2 PA1 -> KEY_BRIGHTNESSDOWN
    gpio3 PB2 -> BTN_TRIGGER_HAPPY2

Open follow-up
--------------
There is no clear vendor path for a dedicated brightness rocker.  The
original RPPOCKET userspace uses Fn + volume up/down for brightness,
with BTN_TRIGGER_HAPPY4 as the Fn key.  The original DTS maps that Fn
code to gpio2 PA4, but PA4 has not fired in our captures.  PA0/PA1/PB2
did fire, but the vendor scripts do not bind BTN_TRIGGER_HAPPY5/6 or
BTN_TL2 to brightness/contrast.

For now, ship working volume and leave brightness as unresolved.  If
brightness is revisited, either wire a ROCKNIX userspace action to the
observed PA0/PA1/PB2 contacts or probe the hardware to confirm whether
PA4 is actually connected.

Things we already tried that ruled out classes of bugs
-------------------------------------------------------
    - Pinctrl is correctly muxing all 6 candidate pins to GPIO with
      pull-up.  Verified at runtime via /sys/kernel/debug/gpio output
      (all 6 lines listed as 'in hi IRQ ACTIVE LOW').
    - All 18 GPIOs request IRQs; gpio-keys is the registered device.
    - The autostart hook's evtest --grab was confirmed as a
      DIFFERENT bug (it blocked ROCKNIX from reading buttons during
      the first ~2.5 minutes of boot).  Removed in commit b03b770f51.
    - We are NOT looking at the amux ADC.  The factory joypad driver
      uses amux only for analog-stick X/Y axes; rocker BUTTONS are
      plain GPIOs.

What is definitely not the answer
---------------------------------
    - "Just use the odroidgo3-joypad driver."  That driver reads the
      same 6 GPIOs the same way; it would not produce different
      events.

Where to look if you pick this up
---------------------------------
    debug/capture.out                most recent test capture (only
                                     press-down 'value 1' events)
    Mounted boot logs                pinmux and gpio state at boot
    /tmp/claude/stock004.dts         decompiled BSP DTB (re-extract
                                     from images/extracted/v1.0.img
                                     if missing)

Honest assessment
-----------------
Volume is resolved.  Brightness is not: the only clear vendor behavior
is Fn + volume, not a separate working brightness rocker.  That is not
blocking the rest of the port.
