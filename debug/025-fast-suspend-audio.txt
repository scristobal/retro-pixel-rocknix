RPPocket fast suspend audio
===========================

Baseline
--------

Branch: retropixel-pocket-support
Committed baseline: 0a12879fc417f86bef7dc41c3e96b41a5fc68fc9
Validated production image SHA-256:
    b2bd07f88fbd9f507ae44f9fb2ac9c61467d306a35ba7687cfaad92a7eba39a4

The user confirmed that short-slider deep suspend, wake, backlight power-off,
Wi-Fi restoration, long-press orderly poweroff, BL31 debug disable, and release
cleanup all work. After ordinary use, the user reported one remaining UX issue:
the early-backlight service makes the screen go dark immediately, but active
audio remains audible for approximately three to five seconds.

Evidence and hypothesis
-----------------------

This matches the accepted suspend timeline. In
`debug/rppocket-power-slider-fast-backlight-v1-journal.log`, the fast service
starts at 159.633130 and reaches sleep.target at 159.797866, while kernel deep
suspend does not start until 163.381912. The regular serial sleep preparation,
including Wi-Fi shutdown, occupies that interval. The normal sleep script does
not mute audio in its pre path, so playback continues until the codec reaches
its later kernel PM callback.

The RK817 codec exposes a two-channel `Master Playback Volume` ALSA control.
Historical RPPocket logs show the corresponding `Master` simple control has
playback volume but no mute switch. Therefore the narrow first candidate is to
extend the already validated early-backlight service, not alter suspend order,
PipeWire policy, the codec driver, or the external-amplifier GPIO.

Candidate A: early ALSA attenuation
-----------------------------------

Change only
`projects/ROCKNIX/packages/hardware/quirks/devices/FunnyPlaying RetroPixel Pocket/002-fast-suspend-backlight`:

1. Blank the backlight exactly as before.
2. Read and retain the exact raw stereo value of the RK817
   `Master Playback Volume` control.
3. Set both playback channels to the codec minimum before notifying systemd
   that the fast service is ready.
4. Keep the service alive across suspend as before.
5. On successful resume, aborted suspend, signal, or timeout, restore the exact
   raw playback values after restoring brightness.

This changes neither the user's PipeWire volume nor the validated serial sleep
preparation. ALSA lookup or write failure is deliberately non-fatal so this UX
feature cannot make suspend unavailable. Long-press poweroff does not start
sleep.target and is unaffected.

Host validation
---------------

Both the installer and generated service script pass `sh -n`.

A command-level mock used a writable fake backlight, suspend-success counter,
and `amixer` implementation. With initial brightness 73 and deliberately
asymmetric playback values 211,197, the state observed at systemd notification
was:

    brightness=0 audio=0,0

After a simulated successful suspend, the exact values were restored:

    brightness=73 audio=211,197

The bounded abort path likewise restored brightness 41 and playback 88,99. A
failed mixer lookup remained non-fatal, left audio unchanged, and still blanked
and restored the backlight around the simulated suspend. No other
hardware-facing variable is changed in Candidate A.

Hardware gate
-------------

Build before flashing. Then, while continuous game audio is playing, perform
one short slider action and verify:

1. screen and sound both stop perceptibly immediately;
2. the backlight remains fully off in deep suspend;
3. one wake action resumes without replay;
4. the prior screen brightness and audio level both return;
5. Wi-Fi restores normally.

Finish with the already validated orderly poweroff and inspect the returned card
before accepting or committing Candidate A.

Hardware result and decision
----------------------------

With continuous game audio playing, the user confirmed that Candidate A works:
the screen and sound now stop together immediately on a short slider action.
Deep suspend and one-action wake still work, and the prior brightness, audio
level, and Wi-Fi connectivity return normally. The user reported the complete
requested gate as working, with no residual-audio or lost-audio issue.

Decision:

    Accept Candidate A. Keep the implementation RPPocket-specific because the
    exact ALSA card/control and RK817 raw-volume semantics are board-specific.
    The broader policy of immediate display/audio suspend feedback may warrant
    a future generic ROCKNIX early-suspend phase, but this direct ALSA mechanism
    must not be applied indiscriminately to other devices.
