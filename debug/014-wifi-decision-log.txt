014 - WI-FI DECISION LOG
==============================================================

Purpose
-------
This file is the running decision log for RetroPixel Pocket Wi-Fi
bring-up.  Append each new experiment here before/after hardware
testing.

current_state.txt should not carry every Wi-Fi trial.  Update
current_state.txt only when a result becomes accepted project state,
usually together with a tested commit.

Rules for each entry
--------------------
Each hardware-facing Wi-Fi experiment should record:

    - date
    - hypothesis
    - code/image change
    - exact test requested
    - observed result from mounted SD logs
    - decision / next step

Current high-level status
-------------------------
[BROKEN] ROCKNIX settings shows Wi-Fi, but scans return no networks.

[FACT]   No Wi-Fi network interface, rfkill device, or iw PHY has
         appeared in any ROCKNIX test so far.

[FACT]   USB host bring-up is working at the root-hub level, but no
         USB Wi-Fi child device has ever enumerated.

[FACT]   SDIO host ff380000.mmc can probe as mmc1, but no test has
         produced an mmc1:0001 SDIO function yet.

[FACT]   Factory v1.1.3 contains Realtek SDIO drivers for RTL8189FS
         and RTL8189ES.  ROCKNIX 6.12.79 currently lacks RTL8189FS/ES
         SDIO aliases/drivers, so even after SDIO enumeration a driver
         port/package may still be required.


2026-04-26 - Baseline failure
-----------------------------
Hypothesis:
    Wi-Fi may already be electrically present and only userspace scan
    or firmware is failing.

Evidence gathered:
    The user reported Wi-Fi appears in settings, but local network
    scans return no results.

Mounted-log result:
    No wlan interface.
    No iw device.
    No rfkill entry.
    No Realtek / rtw / rtl Wi-Fi probe line.

Decision:
    Userspace has nothing to scan with.  Continue below the network
    stack, starting with bus enumeration and power sequencing.


2026-04-26 - USB host bring-up, inherited Odroid wiring
-------------------------------------------------------
Hypothesis:
    The device might use USB Realtek Wi-Fi, and the inherited Odroid
    USB/PHY wiring only needs enabling.

Change:
    Enabled USB OTG/host paths and related PHY nodes.
    Tried Wi-Fi power via GPIO2 PB1 in both active-low and active-high
    forms.

Test requested:
    Flash rebuilt image, boot, try Wi-Fi scan, return SD for mounted
    log inspection.

Mounted-log result:
    DWC OTG root hub appears.
    EHCI root hub appears.
    OHCI root hub appears.
    No USB child appears behind any root hub.
    No Realtek USB device.
    No wlan/rfkill/iw.

Decision:
    USB host controller bring-up is real, but the Wi-Fi device is not
    appearing on USB.  Either Wi-Fi is not USB, the power/reset path is
    still wrong, or USB host is unrelated to Wi-Fi.


2026-04-26 - USB host with factory 5V enable GPIO3 PC3
------------------------------------------------------
Hypothesis:
    USB child enumeration may need the factory board 5V switch rather
    than inherited Odroid GPIO0 PB7.

Change:
    Moved vcc_host to GPIO3 PC3, matching the factory panel property:

        vcc5v_en_gpio = <&gpio3 RK_PC3 GPIO_ACTIVE_LOW>

    In mainline DTS this was represented as an active-high host
    regulator because the vendor panel driver drives the raw GPIO high
    to enable and low to disable.

Test requested:
    Flash rebuilt image, boot, try Wi-Fi scan, return SD.

Mounted-log result:
    USB root hubs still appear.
    GPIO3 PC3 is held high as regulator-vcc-host.
    No USB child appears.
    No Realtek USB device.
    No wlan/rfkill/iw.

Decision:
    The board 5V switch is likely correct for USB host power, but it
    does not expose Wi-Fi as USB.


2026-04-26 - Factory source/DTB comparison
------------------------------------------
Hypothesis:
    Factory source/images should reveal the working bus and power
    model.

Evidence gathered from:
    original-sources/extpackage/linux-kernel-rppocket/
    original-sources/images/
    /run/media/samu/RETROPIXEL1/
    /tmp/rppocket-system-v113/

Findings:
    Factory Linux DTB enables:

        dwmmc@ff380000 / &sdio
        bus-width = <4>
        supports-sd
        card-detect-delay = <800>
        ignore-pm-notify
        cd-gpios = <&gpio3 RK_PB6 GPIO_ACTIVE_LOW>
        sd-uhs-sdr12 / sdr25 / sdr50 / sdr104
        vqmmc-supply = <&vccio_sd>
        vmmc-supply = <&vcc_sd>

    Factory Linux DTB has:

        LDO_REG9 regulator-name = "vcc_wifi"
        regulator-always-on
        regulator-boot-on

    Factory Linux DTB/source panel node has:

        wifi_vcc_en_gpio = <&gpio2 RK_PB1 GPIO_ACTIVE_LOW>

    But the vendor panel-simple.c Wi-Fi GPIO handling block is
    commented out, so the vendor panel driver likely does not drive
    GPIO2 PB1.

    Factory Linux DTB keeps EHCI/OHCI disabled.  USB OTG is okay, but
    there is no evidence that Wi-Fi is behind USB.

    Factory DTB does not contain an obvious wlan-platdata /
    wireless-wlan node for RPPocket.

    Factory KERNEL contains Rockchip rfkill-wlan symbols:

        rockchip_wifi_power
        rockchip_wifi_set_carddetect
        get_wifi_chip_type

    Factory SYSTEM contains Realtek SDIO modules:

        rtl8189fs/wlan.ko
            aliases: sdio:c07v*d*, sdio:c*v024CdF179*

        rtl8189es/8189es.ko
            alias: sdio:c*v024Cd8179*

    Factory Realtek SDIO driver init calls:

        rockchip_wifi_power(1)
        rockchip_wifi_set_carddetect(1)

    before registering the SDIO driver.

Decision:
    Treat Wi-Fi as probably SDIO.  A working solution likely needs:

        1. Mainline-compatible SDIO power/rescan sequencing.
        2. A Realtek SDIO driver if the chip enumerates as RTL8189FS
           or RTL8189ES.


2026-04-26 - SDIO enabled as non-removable with PB1 power gate
--------------------------------------------------------------
Hypothesis:
    GPIO2 PB1 may be the Wi-Fi power/reset gate, and the disabled
    SDIO host needs enabling as a non-removable Wi-Fi bus.

Change:
    Enabled &sdio as non-removable.
    Supplied it from a GPIO2 PB1 fixed regulator / wifi_vcc_en.

Test requested:
    Flash rebuilt image, boot, try Wi-Fi scan, return SD.

Mounted-log result:
    ff380000.mmc probes as mmc1.
    mmc1 reports:

        Failed to initialize a non-removable card

    No mmc1:0001 device.
    No wlan/rfkill/iw.

Decision:
    This proved the SDIO controller can probe, but PB1-as-vmmc/power
    was not sufficient and may be the wrong abstraction.


2026-04-26 - SDIO changed to factory vendor shape
-------------------------------------------------
Hypothesis:
    The factory DTB SDIO node may work better than mainline-style
    non-removable probing.

Change:
    Changed &sdio to mirror factory:

        supports-sd
        card-detect-delay = <800>
        ignore-pm-notify
        cd-gpios = <&gpio3 RK_PB6 GPIO_ACTIVE_LOW>
        sd-uhs-sdr12 / sdr25 / sdr50 / sdr104
        vqmmc-supply = <&vccio_sd>
        vmmc-supply = <&vcc_sd>

Test requested:
    Flash rebuilt image, boot, try Wi-Fi scan, return SD.

Mounted-log result:
    ff380000.mmc probes as mmc1.
    GPIO3 PB6 CD is present and active-low.
    /sys/kernel/debug/gpio shows:

        gpio-110 (cd) in lo IRQ ACTIVE LOW

    mmc1 tries progressively lower speeds:

        400 kHz -> 300 kHz -> 200 kHz -> 100 kHz

    No mmc1:0001 device.
    No wlan/rfkill/iw.

Decision:
    Factory-shape SDIO is not enough under ROCKNIX/mainline.  The
    card-detect line is asserted, but the card does not respond.


2026-04-26 - PB1 unclaimed, factory SDIO retained
-------------------------------------------------
Hypothesis:
    GPIO2 PB1 should not be driven at all because the factory panel
    driver's wifi_vcc_en_gpio handling is commented out.

Change:
    Removed the explicit PB1 fixed regulator / wifi_vcc_en claim.
    Left PB1 unclaimed/input.
    Kept factory-style SDIO node.

Test requested:
    Flash rebuilt image, boot, try Wi-Fi scan, return SD.

Mounted-log result:
    Booted normally.
    vcc_wifi LDO9 is enabled.
    ff380000.mmc probes as mmc1.
    GPIO3 PB6 CD is low/card-present.
    No mmc1:0001 device.
    No SDIO modalias.
    No wlan/rfkill/iw.

Decision:
    Leaving PB1 alone did not make the chip respond.  Need a
    mainline-compatible pwrseq/rescan equivalent, not just factory
    passive wiring.


2026-04-26 - GPIO2 PB1 mmc-pwrseq, factory SDIO retained
--------------------------------------------------------
Hypothesis:
    The factory Realtek driver calls Rockchip power/carddetect helpers.
    In mainline, the closest DTS-level equivalent is mmc-pwrseq-simple
    driving GPIO2 PB1 as reset while the MMC core rescans.

Change:
    Added:

        wifi_pwrseq: wifi-pwrseq {
            compatible = "mmc-pwrseq-simple";
            reset-gpios = <&gpio2 RK_PB1 GPIO_ACTIVE_LOW>;
            post-power-on-delay-ms = <300>;
            power-off-delay-us = <200000>;
        };

    Bound it to factory-style &sdio:

        mmc-pwrseq = <&wifi_pwrseq>;

Test requested:
    Flash rebuilt image, boot, try Wi-Fi scan, return SD.

Mounted-log result:
    Booted normally.
    ff380000.mmc logs:

        allocated mmc-pwrseq

    /sys/kernel/debug/gpio shows GPIO2 PB1 owned as reset:

        gpio-73 (reset) out lo ACTIVE LOW

    mmc1 still only tries bus speeds down to 100 kHz.
    No mmc1:0001 device.
    No SDIO modalias.
    No wlan/rfkill/iw.

Decision:
    pwrseq is wired and executing, but factory removable/CD-style SDIO
    still does not enumerate the chip.  Next isolate card-detect style
    versus non-removable SDIO probing.

2026-04-26 - Pending test: non-removable SDIO + inverted PB1 pwrseq
-------------------------------------------------------------------
Hypothesis:
    GPIO2 PB1 may not be a conventional Wi-Fi reset line.  The factory
    source names it wifi_vcc_en_gpio and marks it GPIO_ACTIVE_LOW, so
    the useful steady state may be physical low.  Using PB1 as an
    active-low reset may leave the chip held off after pwrseq deasserts.

Change:
    Keep the previous non-removable SDIO shape, but invert the pwrseq
    GPIO polarity:

        reset-gpios = <&gpio2 RK_PB1 GPIO_ACTIVE_HIGH>;

Expected GPIO/log signal:
    GPIO2 PB1 should still be owned by pwrseq reset, but the final
    physical level should be the opposite of the previous run.  Look for
    mmc1:0001, an SDIO modalias, Realtek/rtw/rtl probe, wlan interface,
    rfkill, or iw PHY.

Build:
    Verified generated image DTB at:

        build.ROCKNIX-RK3326.aarch64/image/system/usr/share/bootloader/device_trees/rk3326-funnyplaying-rppocket.dtb

    contains non-removable SDIO and:

        wifi-pwrseq reset-gpios = <gpio2 PB1 GPIO_ACTIVE_HIGH>

Decision:
    Mounted-log result:
        Booted expected inverted-polarity DTB.
        DTB contains wifi-pwrseq reset-gpios = <gpio2 PB1
        GPIO_ACTIVE_HIGH>.
        ff380000.mmc allocated mmc-pwrseq.
        mmc1 reported card is non-removable.
        GPIO2 PB1 is now:

            gpio-73 (reset) out hi

        vcc_wifi enabled.
        mmc1 attempted 400/300/200/100 kHz.
        mmc1: Failed to initialize a non-removable card.
        No mmc1:0001, SDIO modalias, wlan, rfkill, iw PHY, or
        Realtek/rtw/rtl probe.

    Inverting PB1 changed the physical steady state but did not make
    the SDIO chip respond.  PB1 polarity alone is not the missing piece.


2026-04-26 - Pending test: SDIO I/O domain on vccio_sd
------------------------------------------------------
Hypothesis:
    The inherited RG351M IO-domain wiring is wrong for RPPocket SDIO.
    Factory RPPocket sets both SDIO and SDMMC IO domains to vccio_sd:

        vccio1-supply = <&vccio_sd>;  /* SDIO I/O Voltage */
        vccio2-supply = <&vccio_sd>;  /* SDMMC I/O Voltage */

    Our current DTB inherited:

        vccio1-supply = <&vcc_3v3>;
        vccio2-supply = <&vccio_sd>;

    That leaves the ff380000 SDIO pin domain configured as 3.3V while
    the SDIO vqmmc rail is 1.8V.  This can prevent the chip from
    answering at the bus level before any Realtek driver can bind.

Change:
    Add an RPPocket override:

        &io_domains {
            vccio1-supply = <&vccio_sd>;
        };

    Revert GPIO2 PB1 pwrseq to the earlier active-low form so this
    experiment isolates the IO-domain correction:

        reset-gpios = <&gpio2 RK_PB1 GPIO_ACTIVE_LOW>;

Expected log signal:
    DTB should show vccio1 and vccio2 both pointing at vccio_sd.
    Look for any change from the existing mmc1 initialization failure,
    especially mmc1:0001 or an SDIO modalias.

Decision:
    Awaiting build and hardware result.

------------------------------------------------------
Hypothesis:
    The main Wi-Fi blocker may be inherited Odroid Go / RG351 board
    policy, not a single missing property.  RPPocket should have its own

        old: #include "rk3326-odroid-go.dtsi"
        new: #include "rk3326.dtsi"

    Recreated explicit board-level nodes for:
        - battery
        - pwm backlight and JDI panel
        - gpio-keys from the factory joypad pin map
        - rk817 PMIC/regulators using RPPocket rail names/voltages
        - vccio1/vccio2 both supplied by vccio_sd
        - SDMMC from factory shape
        - SDIO from factory shape
        - confirmed GPIO hogs for LCD bias and audio amp
        - USB host power through GPIO3 PC3

    This deliberately removes Odroid/RG351 inherited assumptions as the
    default source of truth.

Decision:
    Awaiting build result.
