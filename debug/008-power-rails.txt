008 - POWER RAILS
==============================================================

The RetroPixel Pocket reuses Anbernic-RG351M-class hardware, but the
rk817 PMIC LDO assignments are SHIFTED, and there are extra GPIO power
gates in front of the panel.  Most of the early "screen is black"
debugging on this port traces back to power-rail wiring.

LDO assignments — RG351M (parent) vs RPPocket (this device)
------------------------------------------------------------

                  RG351M (mainline)         RPPocket (BSP/factory)
    LDO_REG1      <not defined>             backlight2v8 supply  2.8 V
    LDO_REG7      vcc_bl       3.3 V        lcd2v8_supply        2.8 V
    LDO_REG8      vcc_lcd      2.8 V        vcc_lcd              1.8 V

LDO_REG1 was the breakthrough.  On mainline RG351M it was completely
undefined, so the LED rail had no voltage at all on RPPocket — no
amount of pwm-backlight wiggling would make the screen visible.  The
factory BSP ALWAYS turns this on.

What we put in the DTS
----------------------

    &rk817 {
        regulators {
            backlight2v8: LDO_REG1 {
                regulator-name = "backlight2v8_supply";
                regulator-min-microvolt = <2800000>;
                regulator-max-microvolt = <2800000>;
                regulator-always-on;
                regulator-boot-on;
                regulator-state-mem {
                    regulator-off-in-suspend;
                    regulator-suspend-microvolt = <2800000>;
                };
            };
        };
    };

    &vcc_bl  { regulator-min-microvolt = <2800000>; regulator-max-microvolt = <2800000>; };
    &vcc_lcd { regulator-min-microvolt = <1800000>; regulator-max-microvolt = <1800000>; };

    &backlight {
        power-supply = <&backlight2v8>;       /* re-route to LDO_REG1 */
    };

    &internal_display {
        compatible   = "jdi,lt031mdz4000";
        iovcc-supply = <&vcc_lcd>;            /* 1.8 V — LDO_REG8 */
        vdd-supply   = <&vcc_bl>;             /* 2.8 V — LDO_REG7 */
        ...
    };

The phandle names &vcc_bl and &vcc_lcd come from the inherited dtsi
and we keep them — even though their semantic meaning is now different
(vcc_bl is no longer "backlight" but the LCD logic 2.8 V; vcc_lcd is
the iovcc 1.8 V).

GPIO power gates (THREE of them)
--------------------------------
The factory BSP's panel-simple.c probe explicitly toggles three
GPIOs to HIGH and never lowers them again:

    gpio_set_value(p->vspn_gpio,    1);   gpio0 RK_PA2  (LCD VSPN)
    gpio_set_value(p->vcc5v_en_gpio,1);   gpio3 RK_PC3  (LCD VCC5V)
    gpio_set_value(p->amp_en_gpio,  1);   gpio3 RK_PC5  (NS4150 amp)

Critically, the vendor DTB had these declared as GPIO_ACTIVE_LOW
(flag 0x01) — but the driver uses RAW gpio_set_value(), not the
active-low aware gpiod_set_value(), so the LOW flag is a red herring.
Physical HIGH = enable on this hardware.

Our DTS expresses each as a gpio-hog pinned to output-high at the
GPIO controller's probe time, with the correct ACTIVE_HIGH flag:

    &gpio0 {
        lcd-vspn-en-hog {
            gpio-hog;
            gpios = <RK_PA2 GPIO_ACTIVE_HIGH>;
            output-high;
            line-name = "lcd-vspn-en";
        };
    };

    &gpio3 {
        lcd-vcc5v-en-hog {
            gpio-hog;
            gpios = <RK_PC3 GPIO_ACTIVE_HIGH>;
            output-high;
            line-name = "lcd-vcc5v-en";
        };
        amp-en-hog {
            gpio-hog;
            gpios = <RK_PC5 GPIO_ACTIVE_HIGH>;
            output-high;
            line-name = "ns4150-amp-en";
        };
    };

History (for posterity, why it took several tries):

    edac723c6c   first attempt: chained 'regulator-fixed' nodes that
                 enabled-via-gpio.  Dependency cycles between panel
                 and DSI controller foiled probe ordering.
    74860fe9c3   second attempt: replaced the chain with three
                 gpio-hogs, but used GPIO_ACTIVE_LOW (echoed from
                 vendor DTB).
    4974fc75b0   FIX: switched to GPIO_ACTIVE_HIGH after re-reading
                 the BSP gpio_set_value calls.  Display lit.

The third GPIO listed in the vendor DTB (vcc_en_gpio on gpio? RK_PB4)
is consumed as an INPUT in the BSP probe (gpio_direction_input) — it
is a state-detection pin, not a power gate.  We do not touch it.

End-to-end power chain on a healthy boot
-----------------------------------------
    vcc3v8_sys  (always-on system 3.8 V)
        -> rk817 LDO_REG1 = backlight2v8_supply  2.8 V  (regulator-always-on)
            -> pwm-backlight power-supply
                -> backlight LED string (PWM-driven brightness)
        -> rk817 LDO_REG7 = vcc_bl(=lcd2v8)       2.8 V
            -> panel vdd-supply
        -> rk817 LDO_REG8 = vcc_lcd(=iovcc)       1.8 V
            -> panel iovcc-supply

    plus:
        gpio0 PA2  HIGH  -> LCD VSPN power switch closed
        gpio3 PC3  HIGH  -> LCD VCC5V power switch closed
        gpio3 PC5  HIGH  -> NS4150 audio amp enabled

Verifying on a running device
-----------------------------
    cat /sys/kernel/debug/regulator/regulator_summary

You should see backlight2v8_supply enabled at 2800 mV, vcc_bl at
2800 mV, vcc_lcd at 1800 mV.  And:

    cat /sys/kernel/debug/gpio | grep -E 'lcd-|amp-en'

should show all three lines as 'out hi'.
